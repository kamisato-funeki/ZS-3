# 开发协作与子代理使用

日期：2026-10-26。导航：[首页](../README.md) · [项目规范](../AGENTS.md)。

## 1. 配置入口与作用范围

仓库根目录为 `code/`。根 `AGENTS.md` 是统一开发规范；`include/`、`src/`、`src/gui/`、`docs/`、`tests/` 下的同名文件补充局部职责。使用标准大写文件名以便工具发现，不另建大小写重复的 agents.md。

项目级设置位于 [config.toml](../.codex/config.toml)，4 个自定义角色放在 `.codex/agents/`。它们使用当前官方格式：每个文件声明 name、description、model、model_reasoning_effort、developer_instructions，由目录自动发现，不使用过时的角色 config_file 映射。

项目配置只在被信任的项目中加载；应从本仓库目录打开新的 Codex 会话，核对角色与并发参数是否生效。当前父会话工作目录可能仍为外层 school-3，不能据配置文件已写入就声称现有会话已热加载。需要的信任在用户明确接受项目时设置，不由本任务改写全局权限。

## 2. 角色、模型和边界

| 角色 | 模型 | 思考强度 | 职责 | 写入权限约定 |
|---|---|---|---|---|
| explorer | gpt-6-luna | medium | 探查文件、资料、数据及依赖，提供证据 | 只读 |
| documenter | gpt-6-luna | high | 需求/设计/测试追踪及文档维护 | 指定 Markdown 文件 |
| coder | gpt-6.1-sol | high | 授权小功能、修复及关联测试 | 指定源码/测试文件 |
| reviewer | gpt-6-astra | low | 独立审查正确性、注释、可读性和验证 | 只读 |

上述只读/写入范围是角色指令和派发约束，不是另行提供的文件系统权限隔离。自定义角色不能依赖不受支持的 sandbox 覆盖来假称强制隔离；实际权限继承运行会话。

主代理负责需求澄清、接口决定、文件分配、验证及 Git 提交。4 个角色是可选择的职责，不代表每次都启动4个代理。配置默认子代理为Luna medium，不改主代理模型；模型不可用时报告，不静默替换。

## 3. 总量和并发

项目角色总量4，不超过5。并发设置 `agents.max_concurrent_threads_per_session=2`，其语义不含主代理，因此包括主代理总共最多3个；这也满足“同时不超过3个子代理”的较宽解释。

禁止子代理嵌套派生。禁止通过外部CLI进程、独立任务或多入口绕过上限。两个槽位已有任务时等待完成/释放，再派下一批；本版不使用第三个子代理槽位。

示例安排：先explorer探查；需求明确后coder和documenter处理不同文件；两者完成释放槽位后reviewer审查；主代理修复、验证并提交。简单文字修改由主代理直接完成即可。

如果宿主使用直接 spawn 接口而没有读取自定义角色，主代理须显式传入角色指定的 model、reasoning_effort 和职责规则；需要指定模型且完整历史继承不接受覆盖时，按宿主要求使用独立上下文并提供必要资料。当前宿主限制比配置更严格时采用更严格限制，不修改配置虚增并发。

## 4. 派发和返回模板

派发必须包含：任务目标、关联需求/设计、允许读取路径、独占写入路径、禁止事项、验收方式、模型/强度和返回内容。共同接口由主代理或单一代理修改，不能两个代理同时改一个文件。所有子代理都禁止 Git 提交和远程操作。

返回包含：结论、改动文件、事实/推断区分、实际执行的验证、未解决问题和建议提交说明。主代理必须查看真实 diff，不能把子代理的“完成”消息直接当作验收通过。

## 5. 注释与可读性验收

根规范对所有变量、常量、结构体、tuple/pair、枚举、函数与lambda都适用。提交前逐项检查：用途是否明确、字段是否齐全、参数/输出是否完整、单位和所有权是否清楚、实现与注释是否一致。自解释命名不免除用户要求的说明注释。

对局部短变量使用简洁紧邻注释；对领域结构和公共接口使用完整Doxygen说明，避免在算法关键处堆砌重复自然语言。声明和定义共享一致契约，定义仍保留紧邻摘要。纯注释变更不得悄悄改变行为。

## 6. 提交与验证流程

完成一个小功能或一个可审核的大改阶段后：查看工作区 → 运行必要检查 → 按明确文件/变更块暂存 → 审查暂存diff与空白错误 → 使用中文说明提交 → 报告短哈希。主代理统一操作，避免子代理共享索引冲突。

类型只用 feat、fix、doc；可带模块scope。此次配置与协作规范提交使用 `doc: 配置模块化注释规范与子代理协作规则`。项目没有首次提交时，已先将此前设计和目录作为独立基线提交，避免与本次新增规则混在一起。

自动commit不等于自动push。没有用户明确要求时保留本地提交；已有用户变更不得混入本任务提交。代码功能需相应测试，配置/文档修改检查TOML解析、配置加载、链接和规则一致性。本次不需要启动模型调用来证明配置文件存在。

## 7. 官方依据与生效限制

依据 [OpenAI自定义子代理说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)和 [AGENTS.md说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)设置。并发字段不包含主线程，角色文件支持独立模型/思考度；项目配置受信任条件约束。

静态检查通过只能说明文件语法与设计约束一致。只有运行时实际发现角色并成功派发，才能说明相应宿主已加载角色；本任务不伪造这类运行结果。精确检查结果见本次交付说明。
